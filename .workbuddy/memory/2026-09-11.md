## 调整：朋友圈多图缩略图尺寸——不要塞满

用户反馈：「现在排版对了，但是大小没做对，你目前都把铺满铺满了，真实微信是会缩小的，你这样太假了」。

### 改前的问题
- 之前 600 画布里把多图设成 146×146、间距 8px，3 列总宽 454px，**直接塞满正文列（455）**。
- 真机微信朋友圈不这样：方块大小是**事先占好的固定格子**，与屏幕宽度解耦，**不会平分到列边缘**。
- 参考：「微信是按事先定义好的格子大小放图片，而 QQ 空间则是按平分屏幕宽度来算的」
  (CSDN《社交应用动态九宫格图片的规则》)
- 「我的 iPhone 6 Plus 一屏如果某条动态有 9 张图片……我至少可以看到二条均带 9 张图片，
  图片占幅不算特别大」——CSDN《微信图片展示规则》给出的 W=250、L=6、Y=180 推算，
  9 宫格总宽约 546/750 ≈ 73%。

### 改后
- `enhance/moments_exact.css` 配图段：
  - 多图（≥2 张）单块 146 → **112**、间距 8 → **6**。
  - 四张（2×2 田字格）同样 112×112。
  - 单图 274×274 → **200×200**（真机单图比多图小一截）。
  - 单图·宽图 (2.5~3:1) 274×109.6 → **200×80**。
  - 单图·超宽图 (>3:1) 454×151.3 → **348×116**（即九宫格总宽）。
- 占正文列 455 的比例：2/4 张约 51%、3/5/6/9 张约 **76%**、单图 44%。

### DOM 实测（`_probe_scene.json` 7 条）
| 类型 | 单块 | 占用总宽 | 占正文列 |
|---|---|---|---|
| 2 张 | 112 | 230 | 51% |
| 3 张 | 112 | 348 | 76% |
| 4 张 | 112 | 230 | 51% |
| 5 张 | 112 | 348 | 76% |
| 6 张 | 112 | 348 | 76% |
| 9 张 | 112 | 348 | 76% |
| 1 张 | 200 | 200 | 44% |

### 关键参考（写入本节以便复用）
- 真机值（CSDN）：W(3 列总宽)=250, L(间距)=6, Y(单块)=180，对应 9 宫格总宽 546，
  占朋友圈正文区比例约 73%。
- 微信公众号 / 全平台规范（allplatforms.io，2026-09 验证）：朋友圈图推荐 1080×1080，
  缩略图渲染在朋友圈信息流中按 1:1 居中裁切；视频 1080×1920 竖版。

## 排障：转账详情推入动画「渐变鬼影」（三重影）根治

## 8080 反复挂掉的完整根因（18:30）
- 现象链：dev server 一下午挂了 4 次（4.5h / 4min / 7min / 1min），最后一次 curl 全 502。
- 三个叠加根因：
  1. vue-cli → internal-ip → default-gateway(win32) 会 spawn `wmic.exe`（程序黑名单），沙箱内外都会被全局拦截杀进程 → 已给两份 default-gateway/win32.js 打补丁（直接 throw，上游都有 try/catch 兜底，LAN URL 显示 unavailable 无影响）。node_modules 补丁 npm install 后会丢，需重打。
  2. 后台 shell（run_in_background）托管的进程跨 turn 不可靠（1-7 分钟内静默死）→ 改用 Start-Process 独立拉起 `node vue-WeChat/_serve8080.js`（detached 包装脚本，stdio 落 _dev8080.log/.err.log），进程完全脱离会话。
  3. **僵尸 node 占端口**：早前死掉的实例留下一个监听 8080 但不响应的 node，导致 curl 全 502、新实例被 vue-cli 自动跳 8081 → 重启前必须查 8080 占位（Get-NetTCPConnection），先杀干净再起。
- 最终状态：独立进程运行、8080=200、2.5min+ 稳定。重启口诀：查端口占位 → 杀多余 node（留 8000 编辑器）→ Start-Process node _serve8080.js → curl 200。
